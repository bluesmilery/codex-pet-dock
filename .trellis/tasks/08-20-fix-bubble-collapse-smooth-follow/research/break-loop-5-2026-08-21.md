# Bug Analysis: 真实图3收起后底座不复位 —— 生产组合证据缺触发等价性

- 日期：2026-08-21
- 角色：第五次 break-loop 根因研究（zhipu/glm-5.3 + max）
- 候选：`<v5-candidate-sha>`；`git diff <approved-product-baseline-sha> -- Sources/` 为空（已复核，产品 Sources 与批准基线一致）。
- 本文件为本次研究唯一写入物；不改 Sources/tests/spec/prd/design/implement，不提交。

## 0. 新的最高可靠性证据（脱敏摘要）

1. 精确 `<v5-candidate-sha>` 归档候选已在真实 Mac 启动，旧实例清场，唯一 executable 路径已核对；无崩溃、无权限弹窗。
2. 真实 UI 确认为用户图3形态：只剩宠物与极小残留条，无会话卡片/圆形控制；WEEK 底座与详情停在屏幕下方旧避让位，超过 9 秒未自动复位。期间底座仍随宠物移动（与既有真机观察一致：跟随活着、避让间距保持）。
3. 自动 T-bv42（手工注入 `targetMissing` → callback → scheduler → FollowLayoutPass → 真实 `DockPanel.frame` 回位）通过，但真实 UI 未产生同等最终状态 → 该测试的触发不是生产等价证据。
4. 视觉截图仅作一次性观察并已删除；不引用会话正文、WID/PID、精确坐标或屏幕内容。

## 1. Root Cause Category

- **Category**: E - Implicit Assumption（主）；B - Cross-Layer Contract；D - Test Coverage Gap。
- **Specific Cause（过程根因）**: v5 把“SCK 成功清单中目标消失（`targetMissing`）”当作真实收起的故障模型。真实图3中残留窗口大概率仍在 SCK 清单中、或根本不走 bubble 探测通道：
  - `PetTracker.obstacleKind` 把高度 < `bubbleHeightMin`(32px) 的障碍归为 `.control`；`FollowLayoutPass.placeDock` 对 `.control` 候选**无条件计入 visibleBounds**（`if pair.1 == .control { return pair.0.bounds }`），完全绕过 BubbleVisibility，也不进入 `bubbleProbe.probe` 的候选集。
  - `defaultCapturer` 只有“清单成功且 WID 不在”才返回 `.targetMissing`；残留窗口仍在清单时返回 `.stats`（细线残留的 alpha 占比可能落在 visible 开阈值之上，见 H2）或 `.unavailable`（保守 visible）。
  - `BubbleCandidateIdentity` 对 bounds/alpha 做**精确比较**；每次 `probe()` 若 identity 变化即 `generation+=1` 并清空 cached/successfullyObserved，`visibility(for:)` 回落默认 `.visible`（见 H4b）。
  因此 T-bv42 证明的是“capture 层若发出 targetMissing，管道会复位”；真实输入大概率不是 targetMissing。产品缺陷根因（障碍为何仍占位）尚未被任何证据区分——这正是本轮要修的过程性根因。

## 2. Why Fixes Failed（逐次）

1. **v1（`<v1-candidate-sha>`）probe 间隔 + coalescer**：修复回调积压，未触及调度相位（surface fix）。
2. **v2（`<v2-candidate-sha>`）stable phase 修复**：补 off-grid wake 与 display-link liveness，但墙钟域混用仍在（incomplete scope）。
3. **v2.5 墙钟统一**：`Date` → 注入单调时钟 + source guard，正确；但不影响本症状。
4. **v3（`<v3-candidate-sha>`）typed outcome**：正确引入 `.stats/.targetMissing/.unavailable`，但当时假设“真机 full-hide 失败 = SCK 清单缺失”。真机复测显示底座跟随宠物却保持旧避让 → 障碍仍被判 visible，故障模型未被 runtime 证据区分（mental model：在 capture 层找答案，未检查 kind 分类层）。
5. **v4（`<approved-product-baseline-sha>`）evidence-only 修复**：把 helper-only 测试升级为生产组合——方向正确，但仍沿用同一故障模型。
6. **v5（`<v5-candidate-sha>`）假阳性的精确定义**：T-bv42 满足“生产组合”（真实 Probe/Scheduler/Coalescer/FollowLayoutPass/`DockPanel.placeBelow`/frame 断言，fake capturer 被 `probe` 真实消费），但**不满足触发等价性**：
   - 测试 fixture 恒为 bubble 几何（高 54 ≥ 32）→ kind 恒 `.bubble`，从未覆盖 control-kind 残留（H1）。
   - fake capturer 直接返回 `.targetMissing` → 模拟“窗口从 SCK 成功清单消失”；真实图3中残留窗口大概率仍在清单（H2 stats-visible / H3 unavailable），或 identity 抖动使结果永远写不进 cache（H4b）。
   - 结论：T-bv42 是 **plumbing 证明**，不是**症状根因证明**。形式上“perturbation → production consumer → observable”全满足，但 perturbation 的 outcome 类型与真实 runtime 分布未验证一致。这是一类新的证据学缺口：生产组合 ≠ 生产触发。

## 4. 高概率假设的强区分证据（隐私安全 runtime telemetry）

### 通用约束

- 只允许输出：**枚举计数、kind、outcome enum、visibility enum、是否回调、障碍数量、匿名 frame relation**。
- 禁止：ID/PID/title/owner/坐标/颜色/文字/图像；不落盘截图；只写 0600 私有文件或内存导出一次性脱敏结构。
- telemetry 本身是产品改动（L2）：需新 campaign 批准 + 完整 Review/QA；默认关闭，仅显式诊断参数启用。

### Probe P0（第一条 discriminating probe，单次采样即可区分 H1/H2/H3/H4b）

在真实图3症状持续期间，按 tick 记录并最终只输出聚合计数：

| 字段 | 类型 | 区分力 |
| --- | --- | --- |
| obstacleCountByKind | `{bubble: n, control: m}` | m≥1 持续 → H1；n≥1 → H2/H3/H4 |
| captureOutcomeByKind | `{stats: a, targetMissing: b, unavailable: c}`（仅 bubble） | c 主导 → H3；a 主导且 visibility visible → H2；b>0 却不复位 → H4a/H6 |
| visibilityEnumByKind | `{visible: x, hidden: y}`（classify 后） | y 主导但仍避让 → H4a/H6 |
| identityChangeCount | Int（`knownCandidates != nextCandidates` 次数 / tick 数） | ≈ 每 tick 一次 → H4b |
| wakeCallbackCount | Int | 回调链活性 |
| dockFrameRelation | 匿名 bucket：`{dy: 0 | (0,32] | (32,64] | >64}`（dock 实际 frame 相对本 tick 无障碍 base frame 的垂直差） | 避让量级与障碍 bounds 高度互相印证，不记录绝对坐标 |

判定矩阵：

| P0 结果 | 结论 | 下一步 |
| --- | --- | --- |
| control ≥1 持续，bubble=0 | H1 确认 | 回规划（障碍几何/control 语义属 PRD Out of Scope） |
| bubble ≥1，outcome stats 主导，visibility visible 主导，identityChange 低频 | H2 确认 | 回规划：脱敏 stats 落点证据 → 重新批准阈值或持续 SCStream |
| bubble ≥1，outcome unavailable 主导 | H3 确认 | 保持保守 visible（**不得把 unavailable 当 hidden**）；单列运行时限制，评估失败细分 |
| bubble ≥1，identityChange ≈ 每 tick | H4b 确认 | 最小修复：identity 比较加抖动容差（与 `positionTolerance` 语义一致）或 identity 变化不整清 cache；红测=在途/静止期 identity 抖动穿透 probe 写回条件 |
| visibility hidden 主导 + obstacle 0 + dy≠0 | H4a/H6 | 第二条 probe：frameSink 输入侧计数（visibleBounds.count vs probe.visibility 输出 vs 最终 frame bucket） |
| obstacle 0 + dy=0 但 UI 仍显示旧位 | 观察分歧（多屏/详情卡独立态） | P1 probe：screenContaining 计数 + detail 跟随计数 |

后续 probe（P1，仅当 P0 落入歧义分支）：frameSink 三点计数（classified 总数 / visibleBounds 数 / `placeBelow` 返回 shown 计数）+ screen id 变化计数（ObjectIdentifier 级，非坐标）。

## 5. 最小 v6 计划

### Phase 0 —— 证据先行（唯一允许先做的改动）

1. 经批准的 L2 campaign：实现 P0 脱敏 telemetry（枚举/计数/匿名 bucket，默认关闭，一次性导出）。改动画布最小：`FollowLayoutPass`/`AppDelegate.tick` 聚合点 + `BubbleVisibilityProbe` 暴露 outcome/identityChange 计数；**不改任何分类、几何、调度、阈值行为**。
2. 真实图3采样 ≥30s（≥300 tick）+ 对照样（expanded 态 + 卡片 collapsed 态各一次）作为基线对照。
3. 按判定矩阵归档结论；任何分支未确认前**不改产品**。

### Phase 1 —— 分支最小修复（各自独立、需证据确认后授权）

| 分支 | 允许的修复 | 边界 |
| --- | --- | --- |
| H1 | 回规划重新批准：control-kind 占位语义如何区分“活跃控制按钮”与“收起残留”（候选：像素观察、CG 元数据、几何稳定性），最小实现以 P0 形态证据为准 | 不预选阈值；不扩大到障碍几何规则之外的改动 |
| H2 | 回规划：以脱敏 stats 落点分布重新批准 alpha 阈值或引入持续 `SCStream`（PRD 已预留该升级路径） | 不在未区分前改阈值 |
| H3 | 保持保守 visible；只允许细分失败原因用于诊断与文档，**不得把 unavailable 判 hidden** | README 运行时限制同步 |
| H4b | `BubbleCandidateIdentity` 相等性加 bounds 容差（≤`positionTolerance`）或 identity 变化只失效受影响 WID；红测必须穿透 `probe()` 写回条件与 `visibility(for:)` 默认值 | 不动 generation/single-flight 安全语义 |
| H4a/H6 | 按 P1 probe 定位后单独最小修复 | — |

### Phase 2 —— 新测试证据拓扑（每分支）

- 红测 fixture 必须复刻**真实触发形态**：H1 → control 几何残留候选穿过 `obstaclesNear → obstacleKind → placeDock`；H2 → 细线占比 stats 穿过 `classify`；H4b → 在途/静止期 identity 抖动穿透 `probe` 写回。全部经真实 `DockPanel.frame` 断言。
- fake capturer 仍可用（管道能力），但每条症状 AC 的主证据必须声明“触发等价来源 = P0 runtime outcome”，否则只能标注 plumbing-only。
- 真机 QA admission：UI 复位观察 + 同一候选的 P0 telemetry 复跑（outcome/visibility/kind 计数转为健康值）双重通过。

## 6. 系统性流程改进

1. **真机 QA admission 升级**：真实症状的通过/失败判定必须附“真实生产 outcome 证据”（枚举级 telemetry），仅 UI 观察/截图只算症状确认，不得作为根因结论或修复验证。
2. **fake/targetMissing 证据降级**：helper/fake 注入一律标注 plumbing-only，只能补充；症状 AC 主证据必须绑定 runtime outcome 等价性。
3. **诊断前置**：今后任何“真机失败但自动全绿”的分歧，第一动作是部署脱敏 runtime probe 区分状态，而非继续在测试里构造新 fake。

## 7. 建议更新的 spec 具体条款（供主 Agent 按 trellis-update-spec 实际写入并同步/提交）

1. `.trellis/spec/macos/quality-guidelines.md` — “验收证据拓扑合同/强制合同”新增 **Trigger Equivalence 合同**：注入扰动的 outcome 类型/分布必须与真实 runtime telemetry 观测一致；未取得 runtime outcome 前的 fake 注入只能标注 plumbing-only，不得作为症状 AC 的主证据或修复验证。准入判定矩阵加一行：“生产组合通过但触发语义未经 runtime 确认 → plumbing-only，不得宣称症状 AC 通过”。
2. 同文件 “硬门禁/真机” 新增 **QA admission 条款**：真机 QA 报告必须包含真实生产 outcome 证据（kind/outcome/visibility 枚举计数 + 匿名 frame relation）；仅 UI 结果不足以判定通过或失败。
3. `.trellis/spec/macos/appkit-conventions.md` 新增 **障碍 kind 与残留窗口条款**：`.control` kind“存在即占位”意味着几何满足 control 的收起残留窗口会永久占位；`BubbleCandidateIdentity` 的 bounds/alpha 精确比较在 CG 抖动下会使 cache 每帧清空、默认 visible。两者修复前都必须有 runtime enum 证据。
4. `.trellis/spec/macos/privacy-guidelines.md` “BubbleVisibility 像素隐私”补充 **runtime telemetry 白名单**：只允许枚举计数、kind、outcome/visibility enum、回调/障碍数量、匿名 frame relation bucket；禁止 ID/PID/title/owner/坐标/颜色/文字/图像。
5. `.trellis/spec/guides/cross-layer-thinking-guide.md` 新增 **Mistake 9：生产组合但非生产触发**（production composition without production-equivalent trigger）及 checklist 项：“每个注入扰动的 outcome 类型是否有 runtime 证据支持”。
