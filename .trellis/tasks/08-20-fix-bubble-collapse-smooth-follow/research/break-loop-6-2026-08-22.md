## 1. 逐项根因分析与最小修复

### P2-1. dy bucket 记录的是请求 frame，不是最终 owner frame

#### 直接证据

当前 DockPanel.placeBelow 先由插值状态得到请求 frame，调用 panel.setFrame(frame, display: true)，然后把同一个请求值传给 dyBucket(actualAppKitFrame:) 并记录。参数名是 actual，但值并不是 setFrame 后的最终状态。

既有 T-re5 测试在断言里单独读取真实 DockPanel.frame，也断言 collector bucket；但两个断言并列，不证明 collector 的输入与写回后的 owner frame 相同。AppKit setFrame 可能做像素对齐、边界约束或其他状态修正；一旦请求值与 owner 值跨过 bucket 边界，真实诊断会误导 H 分支判定。

#### Root Cause Category

- E - Implicit Assumption：假设 setFrame 请求值等于最终 panel.frame。
- D - Test Coverage Gap：测试证明“实际 panel frame 正确”和“collector 有 bucket”，未证明二者同源。

#### 最小 v7 修复

在 panel.setFrame 后立即读取 panel.frame 作为 ownerFrame，仅把 ownerFrame 传给 dyBucket 和 recordDockDyBucket；插值状态继续使用原请求值，不改变布局行为。

必须新增两层可失败证据：

1. owner read-back 行为回归：穿过 FollowLayoutPass → DockPanel.placeBelow → RuntimeEvidenceCollector。使用相对、匿名的 fractional fixture，使请求 dy 位于 bucket 边界上方极小 epsilon，setFrame 像素对齐后落到边界内；断言 collector bucket 等于按写回后真实 panel.frame 独立计算的 bucket，且不等于按请求 geometry 计算的 bucket。禁止机器绝对坐标。
2. owner-read-back absence guard：可执行 source guard 要求 recordDockDyBucket 的输入来自 panel.setFrame 之后的 panel.frame 读回；mutation 把读回替换为请求 frame 时必须 FAIL，撤销 mutation 后恢复 PASS。

若 fractional 行为回归在某个显示环境不能区分请求值与 owner 值，不能宣称行为证据通过；以 mutation guard 记录缺口并加强 fixture，仍不得引入 test-only 第二个 frame owner。

### P2-2. async fixture 用 DispatchSemaphore.wait 阻塞 executor

#### 直接证据

T-re10 的 BubbleCapturer 是 async closure，却调用 DispatchSemaphore.wait() 等待手工 release。这解决了上一轮轮询非确定性，但把同步阻塞 primitive 放进 Swift concurrency 上下文：compiler 报 warning，且等待期间占住 cooperative executor 线程。

现有 zero-warning hard gate 绑定 swift build -c release；tests/main.swift 不属于 SwiftPM target，而是 make test-ui 中单独 swiftc 编译。该编译未把 warning 当 error，所以测试通过并不能证明测试代码 zero warning。

#### Root Cause Category

- A - Missing Spec：zero-warning 要求没有明确覆盖独立编译的 test target。
- C - Change Propagation Failure：测试入口脱离 SwiftPM target 后，release warning 门禁没有传播到 test compile。
- E - Implicit Assumption：把“确定性同步 gate”误认为 async-safe。

#### 最小 v7 修复

把 T-re10 的 blocking gate 改为 test-only async-safe gate：用 lock 保护的 CheckedContinuation<Void, Never> 与 entered 计数实现 suspendAfterEntry() / release()。capturer 进入后标记 entered 并 await 挂起，不阻塞线程；主测试 pump RunLoop 直到 entered/calls/inFlight 状态确定，再注入 identity replacement、断言 single-flight，随后 resume continuation 并等待完成。gate 必须保证 continuation 恰好 resume 一次，并继续覆盖 stale completion 拒绝与第二轮 accepted capture。

把现有 make test-ui 的 swiftc 命令加上 -warnings-as-errors，形成可失败的 test compile gate。mutation 证据：临时恢复 DispatchSemaphore.wait 版 fixture 时 make test-ui 必须在编译阶段 FAIL；撤销后恢复 PASS。release 0 warning 门禁保持不变。

### P2-3. privacy guard 非递归且未证明 production sink

#### 直接证据

当前 Python guard 用 Path.glob("*.swift") 只枚举 Sources/PetDock 第一层；Sources/PetDock/Data/*.swift 等嵌套 production source 不会进入扫描。它只断言 RuntimeEvidenceCollector( 构造点总数为 1 且位于 main.swift，没有断言该构造点的 outputURL。

当前生产代码事实上在 main.swift 用 PrivateStorage.diagnosticsURL.appendingPathComponent(RuntimeEvidenceCollector.outputFileName)，但这是人工读码结论；guard 本身无法阻止唯一构造点改写到非私有 sink，也无法发现嵌套 source 里的第二个构造点。

#### Root Cause Category

- C - Change Propagation Failure：source tree 有嵌套目录，guard scope 没有随之递归。
- D - Test Coverage Gap：guard 断言了构造点计数，却没有断言更关键的 sink invariant，也没有 mutation 证明。

#### 最小 v7 修复

将 production constructor guard 改为 rglob("*.swift") 递归枚举 Sources/PetDock（继续排除 RuntimeEvidence.swift 自身），并保持唯一构造点位于 main.swift。同一测试对 main.swift 做空白归一化后断言精确 sink 表达式：PrivateStorage.diagnosticsURL.appendingPathComponent(RuntimeEvidenceCollector.outputFileName)。

必须记录两类 mutation，均在撤销后复跑通过：

1. 在嵌套 production Swift source 中临时加入第二个 RuntimeEvidenceCollector( 构造点，递归 guard FAIL，证明 scope 可失败。
2. 临时把 production outputURL 改为非 Diagnostics URL，sink assertion FAIL，证明私有 sink contract 可失败。

RuntimeEvidence.swift 自身的 aggregate-only guard 继续保留；不要把测试 fixture 的临时 output URL 当作 production sink 证据。

### P2-4. full SHA 文档合同与 parser/test 不一致

#### 直接证据

开发候选验证文档和 quality spec 要求 QA 用完整候选 SHA 绑定 runtime evidence；当前 parser 注释和实现接受 7–64 位小写十六进制，测试还显式把 7 位 short SHA 判为合法。这样 7、39、41、63、64 位输入都可能成为“合法” provenance，而样本未必绑定冻结完整提交。

#### Root Cause Category

- B - Cross-Layer Contract：docs、parser、test 三层对 full SHA 的定义不同。
- D - Test Coverage Gap：测试复述实现的范围检查，没有从文档合同生成边界反例。

#### 最小 v7 修复

当前仓库为 SHA-1 对象格式，合同应固定为“恰好 40 个小写十六进制字符”。更新 isCandidateSHA 与注释；测试使用占位 full SHA，并显式拒绝 7、39、41、64 位、大写和非十六进制。docs/spec 只需把“完整候选 SHA”落成同一 40-hex 语义。若未来迁移 SHA-256，必须同一提交更新 docs/parser/tests 为明确的全长对象格式合同，不允许恢复任意长度区间。

## 4. 只有文字、缺少 executable gate 的规则

1. “0 warning”只约束 release build；独立编译的 UI test target 没有 warnings-as-errors。
2. “最终所有者必须是实际 panel frame”没有落实为 telemetry 输入 provenance 检查。
3. “诊断只能进私有 Diagnostics”有行为测试和人工源码事实，但没有递归 constructor/sink source guard。
4. “runtime evidence 绑定完整候选 SHA”没有 docs-parser-test 同源合同；7–64 位区间被测试固化。
5. AC Evidence Topology Table 是人工叙述；main admission 没有机械复核每个 claimed owner 的实参来源。
6. static guard 的可失败性没有统一要求 mutation 证据；已有 cadence guard 曾做 mutation，但 runtime privacy guard 没有继承该纪律。
