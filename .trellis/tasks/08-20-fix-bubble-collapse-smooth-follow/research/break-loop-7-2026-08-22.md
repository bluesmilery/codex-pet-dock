## 0. 结论摘要

v7 对 `<v7-r2-review-base>` 的第二轮 formal Review 报告 P0=0/P1=0/P2=2（构造守卫逃逸），流程熔断：无 QA、无第三轮补丁。两项 finding 均可在当前树直接复核：

1. **定义文件豁免洞（A）**：privacy guard 按精确相对路径排除根级 `RuntimeEvidence.swift`，因此可在该文件内新增接收任意 `outputURL` 的 static factory/singleton；外部调用 `RuntimeEvidenceCollector.<factory>(...)` 不匹配 direct/`.init`/metatype/typealias/typed-init 任何一种被禁形态，guard 仍 PASS。任意生产 sink 由此可表达。
2. **注释 trivia 洞（B）**：guard 的归一化只去空白。Swift 中注释与空白同为 trivia：`RuntimeEvidenceCollector /*...*/ (` 与 `RuntimeEvidenceCollector /*...*/ .init(` 都是合法构造语法，但空白归一化后分别得到 `RuntimeEvidenceCollector/*...*/(` 与 `RuntimeEvidenceCollector/*...*/.init(`，全部不命中被禁 token 序列，guard 仍 PASS。且 Swift 块注释支持嵌套、字符串字面量内可出现任意形态——正确的“去注释”本身就是一个小型词法器，已被任务明确排除（不得 homemade parser）。

本研究的核心判断：**这不是第五、六个还没枚举到的语法变体，而是一类不可收敛的防御范式错误**。构造一个类型没有任何“跨文件不可避免的固定 token 序列”（类型名可 typealias、可由类型注解推断后 `.init`、可先取 metatype 再调用、可被注释 trivia 分隔），因此“构造语法 absence”根本不是文本检查能可靠回答的问题；它恰好是 Swift 访问控制（`private init`）原生回答的问题。v8 应把该不变量交还编译器，文本守卫收缩为守卫擅长的事：单一 token 存在性/布线计数。

## 1. Root Cause Category 与各阶段漏检分析

### 1.1 类别

- **主类别 E - Implicit Assumption**：隐含假设“空白归一化文本 ≈ Swift token 流”。注释（含嵌套块注释）、字符串字面量都是合法 trivia/字面量，空白归一化对它们无效；该假设从未被写下或证伪。
- **副类别 A - Missing Spec**：缺少“哪类不变量由哪层保证”的分层合同——编译器/访问控制、单一 token 文本守卫、正式 Review 各自的职责边界没有规范，导致语言级不变量被放进了文本扫描层。
- **失败形态**：Surface/Incomplete Scope + Tool Limitation。每轮修复都是在 regex 家族内追加被报告的那一个变体（r1：嵌套 `.init`/同名文件；r1 批次内追加：多行 typealias/无括号 factory reference；r2：定义文件豁免与注释 trivia），枚举永不封顶。

### 1.2 为什么实现、trellis-check、main admission、r1 修复与 pre-r2 admission 全部漏检

| 阶段 | 行为 | 漏检机制 |
| --- | --- | --- |
| v7 实现 | 按第六次 break-loop 最小修复合同把 guard 从 glob 改 rglob 并加 sink 断言 | 合同只要求“递归 + sink 断言”；实现选择 regex 形态时没有攻击者模型（“编译器接受而 regex 不匹配的形态有哪些”），只覆盖手头被报告的形态 |
| trellis-check 自检 | 复跑 gate + 为已报告形态做 mutation FAIL/PASS | mutation 从作者同一心智模型生成：模型里没有“注释是 trivia”“定义文件自身可建 factory”，mutation 就永远测不到想象之外的逃逸 |
| main pre-Review admission | 逐行审计 topology 表：计数、命令、mutation 记录齐全 | 程序完整性审计，不是对抗性词法分析；表格字段没有“守卫范式是否可收敛”这一项 |
| r1 修复 + second-review admission 追加修补 | 追加 `.init`/metatype/typealias 绑定正则（含关键字边界的多行惰性正则）、禁止无括号 first-class constructor reference | 典型枚举回应：每加一条 pattern，regex 复杂度上升，但底层“文本无词法器”缺口原样保留；关键字边界正则自身又引入新的误报/漏报面 |
| r2 Reviewer | 站在编译器视角问“编译器接受而 regex 不匹配的形态还有什么” | 立刻找到两个模型外形态（定义文件内 factory、注释 trivia 分隔）。这正是不可 by-枚举证伪防御的签名 |

### 1.3 Bayesian priors → posteriors

Prior 取自“同一守卫两轮 Review 后仍有逃逸”这一条件，读当前源码/测试前：

| 假设 | Prior | 依据 |
| --- | ---: | --- |
| H1 词法不可表示：任何空白归一化 regex 都无法建模 Swift trivia/嵌套注释/字符串，枚举不可收敛 | 50% | 该 bug 家族的直接形态 |
| H2 层次错配：构造唯一性/固定 sink 本应由访问控制保证，放在文本层是结构性 incapable | 30% | `private` 恰好提供所需语义且从未被使用 |
| H3 流程缺口：守卫无书面攻击者模型与 mutation 矩阵，各阶段只能验证“报告过的形态” | 15% | mutation 全部追认已报告 finding |
| H4 有意豁免或 spec 冲突 | 5% | 无任何授权/文档支持豁免 |

证据（直接、可复核）：① 五轮修补全部停留在 regex 家族内；② r2 两个洞都完全不在“调用点语法”模型内（一个在豁免文件内部，一个在 trivia 层）；③ 当前 guard 源码确认空白归一化 `"".join(source.split())` 与按相对路径豁免定义文件；④ Swift 嵌套块注释使“去注释”本身成为词法器问题。

| 假设 | Posterior | 说明 |
| --- | ---: | --- |
| H1 词法不可表示 | 40% | 与 r2 洞 B 直接吻合 |
| H2 层次错配 | 38% | 与 r2 洞 A 吻合：regex 连“谁能构造”都无法表达，而 `private` 一词即答 |
| H3 流程缺口 | 19% | 解释各阶段为何只能追认 |
| H4 有意豁免 | 3% | 无证据 |

- **置信度：regex 范式不可收敛 ≥95%**（嵌套注释+字符串字面量已足够；且正确实现即 homemade parser，被任务禁止）。
- **置信度：v8 结构方案消除“外部任意构造/任意 sink”这一类问题 ~90%**：调用点由编译器封死（双侧配置），定义文件内新增 API 由 token canary + 正式 Review 合同覆盖；残余风险见 §2.6。

### 1.4 可推广的守卫分层原则（本轮最重要的知识）

1. **单一 token absence 守卫是可靠的**：若被禁行为必然包含某固定单一 token（如调用 Timer API 必含 token `Timer`；引用测试工厂必含其标识符），substring 检查在逃逸方向上不可绕过——注释无法切进标识符内部；注释/字符串包含该 token 只会造成 fail-closed 误报（安全方向）。现有 aggregate-only guard（banned API/字段 token 表）因此历经多轮 Review 存活。
2. **构造语法 absence 守卫不可靠**：构造一个类型没有跨文件不可避免的 token 序列（别名、推断、metatype、trivia 分隔均合法）。这类不变量必须交给访问控制/签名，不得用 regex 表达。
3. **declaration shape 只能防 accidental drift**：行首锚定、精确计数的 declaration canary 可防普通重命名/移除，但注释、字符串或 inactive conditional 中的诱饵仍可能满足文本 presence。它不得作为安全主证据；访问控制必须由外部构造编译 probe 独立证明。
4. **mutation 必须来自独立模型**：自检 mutation 若全部由守卫作者生成，只能证伪作者已想象的形态；privacy 表面的 mutation 矩阵必须至少各含一条**编译层**与一条**布线层**反例（见 §4）。

## 2. 结构化方案评估（任务指定项逐条）

### 2.1 `private init`（推荐，P0）

把 `RuntimeEvidenceCollector` 的 designated initializer 改为 `private`。效果：**任何其他文件**（含 main.swift、嵌套 source）无论用直接构造、显式 `.init`、metatype、typealias、类型注解推断还是注释 trivia 分隔，编译期一律失败——r1/r2 已发现的与未发现的全部语法变体一次性不可表示。Swift 的 `private` 对**同文件 extension** 可见，因此工厂必须与 private init 同文件（`RuntimeEvidence.swift`）。`final class` 也排除子类化逃逸；类为纯 Swift（非 `@objc`），不存在 ObjC runtime 反射构造路径（残余 exotic 路径见 §8）。

### 2.2 生产工厂：只收 SHA/时钟，硬编码私有 sink（推荐，P0）

`static func production(candidateSHA: String, flushNow: @escaping @Sendable () -> TimeInterval) -> RuntimeEvidenceCollector`

工厂只接受 QA 合法可变的输入（已验证 40-hex 的 SHA、注入时钟）；sink 在定义文件内部硬编码为 `PrivateStorage.diagnosticsURL.appendingPathComponent(outputFileName)`，**签名不含任何 URL 参数**。于是“任意 outputURL”在所有生产调用点不可表达（参数不存在，传了就编译失败），且 v7 在 main.swift 参数区做括号配对的脆弱 sink 断言可整体删除——sink 合同住进类型自身。main.swift 改为 `RuntimeEvidenceCollector.production(candidateSHA:flushNow:)`。

### 2.3 测试专用工厂 + 独立编译 flag（推荐，P0）

现有 9 处测试构造需要自定义临时 URL（sink 权限/symlink 拒绝/节流/重试测试），private init 后不可直连。方案：在同一文件内加 `#if PETDOCK_TESTING ... #endif` 包裹的 `static func forTesting(candidateSHA: String, outputURL: URL, flushNow: ...) -> RuntimeEvidenceCollector`（同文件访问 private init；名字是单一 token，任何外部引用都留下不可分割的标识符痕迹）。测试不访问其他私有内部：tests 经 swiftc 直编全部源码（同 module），internal API 天然可见，无需 `@testable`、无需为测试放宽任何生产访问级别。

### 2.4 Makefile flag + release 证明（推荐，P0）

- Makefile `test-ui` 的 swiftc 命令加 `-DPETDOCK_TESTING`（全仓唯一一处）。
- release 走 SwiftPM `swift build -c release`；`Package.swift` 无 `swiftSettings`/define（守卫断言 token 不出现）→ `#if PETDOCK_TESTING` 区域在 release 词法阶段被排除。
- **release 缺席的可执行证明 = 编译 mutation**（§4 MA5/MA6），不采用对二进制做符号扫描（mangling 脆弱且非合同）；“生产源码引用 forTesting → release 编译失败”即最强证据。

### 2.5 是否移动类型/文件；测试如何访问私有内部

**不移动**。① 工厂必须与 private init 同文件（访问控制是文件作用域），搬走即失效；② 拆 library target + `@testable` 属大型结构 churn，且 module 边界并不解决任意 URL（internal init 对全部生产文件可见，恰是洞 A 的放大版）；③ tests 现行走 swiftc 文件清单直编，target 重构会破坏 test-data/test-shell 既有编译方式。测试对私有内部的全部需求由 forTesting 覆盖，不需要任何其他后门。

### 2.6 残余威胁的诚实分层

| 威胁 | v8 后由谁保证 | 证明方式 |
| --- | --- | --- |
| 外部文件任意语法构造 | 编译器（private init） | MA1–MA3 release 编译 FAIL |
| 调用点传任意 URL | 编译器（生产工厂无 URL 参数） | MA4 release 编译 FAIL |
| release 含测试工厂 | SwiftPM 无 flag + 词法排除 | MA5/MA6 编译 FAIL + 布线守卫 |
| 定义文件内新增未 flag 的 URL 型 API / 裸露测试工厂 | **编译器不管**（同文件 private 可达）：token canary + 正式 Review 合同 | MA8/MA9 守卫 FAIL；spec 规定该文件 API 面变更必须隐私复审 |
| 文档/布线漂移（flag 进 Package/Makefile 他处） | 布线守卫（单一 token/计数） | MA6/MA7 |

同文件新增 API 是访问控制语言的固有余地（无 friend/更细粒度）；对策是把 `RuntimeEvidence.swift` 保持为小文件 + canary + Review 合同，而不是继续造 regex。
